# Full source-video review

Resolve `SKILL_DIR` to the installed video skill and keep cwd in the chosen project. Read this only for a new complete video analysis; focused follow-ups use only relevant gates and source intervals.

Turn a local video path into an evidence-backed workout timeline. Prefer local signal processing over model-visible frames; spend visual tokens only where classification, counting, or form judgment requires them.

## Counting context and source evidence

Default to `source_review` when targets, previous counts or user corrections are already present in the conversation. They are comparison material only after per-set source events are locked, never evidence for repetitions. Do not claim the model can forget them. Use `blind_source_review` only in an actually isolated context that received no expected totals; record the isolation basis. Do not automatically spawn agents merely for this purpose.

Never infer repetitions from duration, cadence, motion peaks or neighboring sets. Count complete cycles in each set's own source frames. Keep reported user counts separate from visual counts and compare them after event locking.

## Mandatory visual count protocol

Use this protocol for every set. Do not announce, save or register an exact count until all steps pass.

1. **Boundary pass without counting.** Review the padded chronological context while deliberately ignoring how many repetitions may be present. Mark the first frame where stable working cycles begin, the last frame where the final complete cycle returns, and every visible setup, equipment adjustment, test movement, pause, release and transition outside that interval. If the work interval cannot be separated from setup or transition, the exact count is unresolved.
2. **Forward event pass.** Starting from the locked work interval, scan chronologically and write one event record only after directly observing boundary–opposite–same-boundary. Record partial, uncertain and excluded movement when encountered. Do not choose or estimate a total first; derive the count only after the event list is finished. A repeated text description or a structurally valid JSON record is not evidence that its frames show the claimed phases.
3. **Reverse audit.** Starting at the end of the same work interval, recount complete cycles backward by writing a separate reverse event list before matching it with the forward list; do not manufacture the reverse list by reversing the forward JSON. Then match the forward and reverse cycles one by one by source timestamp. If the passes disagree, densely rescan the disputed interval. If they still disagree or any interval is unseen, report the known events and unresolved interval instead of an exact high-confidence count.
4. **Anti-fabrication check.** Never generate event timestamps from a desired count, average cadence, duration, arithmetic progression or evenly spaced template. Never bulk-fill phase labels, observations, classification fields or confidence for events that were not individually viewed. Each complete repetition needs three distinct source frames that were actually inspected and that visibly show the declared phases. Missing or ambiguous return frames make the event partial or uncertain, not complete.
5. **Final self-check.** Before exposing a count, answer all of these from the current source frames: Was the work interval selected before counting? Were setup and adjustments excluded? Was every complete cycle individually observed? Did the reverse audit reproduce the same cycles? Are there no unseen or unresolved gaps? Was the result based on observed cycles, and was prior exposure honestly declared? If any answer is no, do not provide an exact count and do not claim high confidence.

## Workflow

1. Resolve the supplied file or folder. List supported videos and sort naturally. Use only file identity and fingerprints to avoid duplicate decoding; do not read prior analysis content before the source-local event count is locked. Do not copy full videos into the project.
2. If present, use the project's `README.md`, `plan.md`, `progress.md`, latest `logs/`, and latest `form-reviews/` only after the source-local event count is locked, and only for naming, archival placement and coaching context. Do not expose their repetition targets or prior counts to the visual counting pass.
3. Before any model-visible frame extraction, run the bounded decoder entrypoint using its permitted execution environment and exact entrypoint: `python3 SKILL_DIR/scripts/workout_video_decode.py prepare INPUT... --output-dir TEMP_DIR --cache-dir PROJECT/.workout-video-cache`. On macOS use the approved bounded decoder route when hardware initialization requires escalation; never copy an author-specific permission assumption. The entrypoint enumerates, naturally sorts, probes, fingerprints, and groups files into continuous recording chains. Continuity requires compatible video geometry plus adjacent recording clocks (and adjacent DJI sequence numbers when present). Do not merge an unexplained gap. Treat the generated `segment-map.json` as the authority for translating unified time back to original file/time.
4. Analyze one fingerprint-keyed, low-resolution, no-audio proxy per chain. With adequate keyframe density, the default proxy is a single-threaded keyframe-only software decode because it is the fastest discovery path. Otherwise the entrypoint uses a hardware-only zero-copy VideoToolbox proxy and fails visibly on silent fallback. Every proxy is `coarse_only`: use it only to discover candidate activity. Never derive exact set boundaries, repetition counts, or form findings from proxy duration or proxy frame positions. Use `keyframe_time_map_path` and `segments` to translate candidates to original files. A set may cross a file boundary and remains one set.
5. Run `SKILL_DIR/scripts/extract_video_signals.py PROXY --cache-dir CACHE_DIR --hardware never` at 1-2 fps and about 96 px wide for the coarse pass because the proxy is already small. Process long sources serially on one decoder. Use motion curves only as navigation evidence, never as final exercise labels or authoritative rep counts. Do not extract or inspect audio unless the user explicitly requests audio analysis.
6. Build candidate sets hierarchically:
   - Use motion starts/stops, posture resets, leaving the exercise position, and camera cuts.
   - Treat a brief top/bottom pause as part of the same set unless the person clearly resets or changes activity.
   - Register every candidate with `SKILL_DIR/scripts/analysis_manifest.py MANIFEST.json --candidate-set SET_ID`; a coarse candidate count is not a completed-repetition count.
7. Apply the classification evidence gate before naming or counting a candidate:
   - Review the wide chronological context first and write down the person's apparent task: working set, setup/equipment adjustment, transition, or ambiguous. Only after this intent pass says `working_set` may you select cycle triplets. Do not infer intent by counting repeated joint positions first.
   - A working set requires at least two repeated complete cycles with a stable load-bearing configuration. Prove each cycle with an ordered boundary-to-opposite-phase-to-same-boundary sequence, such as top-bottom-top; two isolated top/bottom poses are not two cycles. Exclude setup, kneeling, stretching, equipment adjustment, and post-set collapse even when they resemble an exercise pose.
   - Inspect the complete body and nearby support/equipment at the top, middle, and bottom of at least two cycles. Use a wider crop or short low-resolution clip when a hand, foot, knee, bench, or weight is outside or near the edge of sparse frames.
   - Record the movement axis, persistent support contacts, joint path, and equipment/environment anchors. Require at least two positive exercise cues plus one cue that excludes the closest look-alike. A pose alone is not an exercise label.
   - Treat a contact as load-bearing only when it persists through the moving phase of at least two cycles. A knee touching during setup or after the last repetition does not make a push-up a knee push-up.
   - If the exercise family is clear but a variant discriminator is hidden, report the family label plus the unresolved variants and separate family/variant confidence. If the gate is not met, use an explicit ambiguous label with alternatives and medium/low confidence; do not promote a guess to high confidence.
   - If source-local review proves that a coarse candidate is setup, transition, equipment adjustment, or post-set movement, register structured evidence with `disposition=non_set` and excluded events, source frames and concrete reasons. A dismissal label alone does not satisfy the completeness gate.
   - Clothing touches, strap/glove handling, checking a weight, rubbing or holding a body part, and irregular arm testing are setup/adjustment cues. These cues override apparent elbow or shoulder oscillation until a separate, stable work interval begins.
8. Reconcile exercise labels and filming setups before counting, but count every set independently under the source-evidence protocol. Cluster sets with the same support configuration, equipment anchors and movement axis only to audit classification and choose review windows. Do not inspect or propagate another set's repetition total. After all per-set counts are independently locked, count differences may trigger a fresh source review but may never be corrected toward agreement merely because the sets look similar.
   - Treat every one-off variant and every candidate whose support configuration differs from the other candidates in the current source as an audit trigger. Review it twice in this order: first a wide chronological sequence for intent and setup behavior, then phase triplets for movement cycles. The two passes must independently agree on the exercise and rule out equipment/clothing adjustment. If they disagree, relabel the segment as preparation/transition or explicit ambiguity. Do not create a new catalog entry during the same pass used to justify the label; add it only after this audit passes.
9. Before source-local review, read [count-evidence.md](count-evidence.md) completely. Translate padded candidates through the segment map and use the unchanged bounded `workout_video_decode.py window` entrypoint. Cover preparation, first/last cycles and post-set reset. Extract review pages only with `extract_review_frames.py`, which validates windows, automatically paginates and records actual frame times/hashes. Do not hand-build a single fixed-capacity tile for a longer interval. Source decoding success alone does not establish that the exercise boundaries were observed.
10. Select the actual work interval before counting. Motion, similarity and tracking results remain navigation candidates until full cycles are visually confirmed; ROI-dependent disagreement triggers targeted review. Save structured per-event boundary–opposite–boundary frame references, including partial/uncertain/excluded events, under the evidence contract. Verify first two, middle, last two and irregular cycles, excluding setup and release. Register with `--evidence SET_ID=JSON`; final counts are computed from confirmed event records. For corrections, preserve old durable revisions and retain predicted-versus-reviewed results. Do not label assistant-reviewed values as user ground truth unless the user actually supplied them.
11. Trigger dense confirmation when any of these occurs: low confidence, disagreement between visual and signal counts, irregular cadence, a suspected partial rep, an exercise transition, a technique problem, failure of the classification evidence gate, or surprising variation among visually similar sets of the same exercise. Cover two complete reps before and after when they exist; at a set/source boundary, document that limit and include the available preparation/reset instead. Within the suspicious movement phase, inspect source frames or sample at no more than 0.1-second spacing; record the actual scanned frame/time range.
12. Use the project's stable `exercise_id` and `issue_id` catalogs when present. Make the model select IDs and evidence; obtain standard names, correction cues, and stop rules from the catalogs. Use `unmapped.*` only when the catalog genuinely lacks the case. Catalog membership never proves that an exercise or issue is present in the video.
13. Apply the problem gate before creating any issue card. A visible property is not yet a problem. Require either a visible technique failure (for example slipping, collapsing, losing balance, or a repeated joint/control deviation) or a user-reported symptom tied to the movement. Material, padding, furniture, footwear, body proportions, or camera appearance alone do not qualify. A comfort aid such as padding on a hard edge is acceptable unless the video shows that it impairs stability or the user reports a problem. Record the criterion, observed violation, and visible movement effect or user-report reference in `problem_gate`, then report the exact timestamp, affected repetition or phase, evidence, confidence, and correction. Separate visible facts from inferences and from user-reported sensation.
14. Save one representative source screenshot for every confirmed issue. The image must show the stated problem and remain seekable through the reported source timestamp.
15. Run `SKILL_DIR/scripts/generate_issue_gifs.py INPUT.json OUTPUT_DIR --update-json` after issues are confirmed and while the source still exists. Generate one short 3-6 second, 8-12 fps, 480-640 px GIF per issue, covering the problem repetition plus nearby context. GIF generation is local and must not trigger another model pass. When the source exists, a confirmed technique issue without its GIF is incomplete and the report must not be presented as finished. If an older source is genuinely unavailable, retain the screenshot and timestamp, record the unavailable source path, and visibly state that the GIF could not be rebuilt.
16. Before drafting totals, run `SKILL_DIR/scripts/analysis_manifest.py MANIFEST.json --assert-final-ready`. Resolve missing or unverified candidate sets instead of silently omitting them. Then build the structured report JSON described in `references/report-schema.md`.
17. Validate schema-5 report evidence bindings and v3 event evidence with the strict renderer. In a project with an existing workout-page workflow, use its integration renderer (`PROJECT/scripts/render_workout_review.py` in compatible projects) to extend the existing workout page; the skill standalone `SKILL_DIR/scripts/render_html_report.py INPUT.json OUTPUT.html` is for projects without that workflow. The strict renderer reopens structured evidence and rejects mismatched totals, sources, segments, confidence or missing sets. It also rejects issue cards without an allowed problem basis, criterion, observed violation, and visible effect or user-report reference. Keep schemas 3 and 4 readable for existing reports only. Use `--allow-legacy` only for explicit historical schema-v2 rendering, visibly labelled as not revalidated. Under `form-reviews/`, it refreshes the report index. Validate one GIF, totals, tutorial links, cross-file segments and same-tab dashboard link.
18. If the project uses the standard fitness layout, run its deterministic durable-data migration, audit, coach snapshot, CSV export, and bookmark-page refresh after the report passes. For projects with `data/workouts/` and `SKILL_DIR/scripts/training_pages.py`, associate the actual canonical records with the existing workout ID, preserve its training-before plan, add concise conclusions to its `review`, and rebuild the same `workouts/<workout_id>.html` URL plus `dashboard.html`. Read the chosen project’s `docs/workout-pages.md`, or the companion coach skill’s page contract for save-workout fields. The same page must contain the preserved plan, actual results, complete analysis, phase boundaries, detailed timeline, GIF evidence and cost. A detail link, second webpage or iframe is not a substitute. Analysis JSON and media may remain separate files; they are rendered into the workout document. Old standalone report HTML may redirect to that workout URL. Deliver only the workout URL. Plans are never completed sessions. With multiple workouts on a date, use explicit session_ids rather than guessing. Other projects may continue embedding coach state and the report index in their dashboard. The permanent `file://` bookmark must work without a server or port. The durable session JSON is the long-term source of truth. Derived HTML, indexes, coach state, and Markdown summaries must remain rebuildable. Preserve source paths, source segments, and fingerprints; never overwrite a prior confirmed revision without archiving it.

## Trackable issue and technique-focus documentation

Every confirmed actionable form deviation shown to the user must become a durable visual evidence bundle, not a text-only observation. This includes both problem-gate issues and lower-severity technique focuses such as a repeatable alignment or setup choice that is worth changing. Keep the problem gate strict: only qualifying problems enter `issues` or increase the issue count. Track a lower-severity correction separately as a `technique_focus` (or the report schema's equivalent), and label it as a technique focus rather than a safety problem. Do not manufacture either record type for a harmless visual property merely to populate the bundle.

When an actionable `technique_focus` does not belong in canonical `issues`, give it the same source/timestamp evidence in a generator-compatible input, create its GIF while the source exists, and bind the resulting asset to the durable report or dashboard focus record without changing the formal issue count.

For each confirmed issue or actionable technique focus, persist and keep mutually consistent:

- session ID, training date and session label
- stable `exercise_id` and `issue_id`, plus the displayed Chinese names
- affected set index and side, and the repetition or movement phase when visible
- original source file, source-relative timestamp, GIF window and source fingerprint
- its record type (`issue` or `technique_focus`); for an issue, the problem-gate criterion, observed violation and visible effect or user-reported symptom; for a technique focus, the visible actionable basis; plus confidence, correction cue and stop rule when applicable
- representative screenshot, local GIF path and the HTML report path

The HTML report and any dashboard/current-priority card that surfaces the issue or technique focus must place the GIF beside an explicit training date, affected set/side and original-file time range. Never show a generic correction without saying which recorded training it came from. Keep paths relative in portable HTML while retaining the original absolute source path and fingerprint in durable data.

Before completing the report, verify that every surfaced issue or technique-focus record resolves to its GIF, screenshot, source mapping and report/dashboard card, and that the displayed date/set/time match the durable record. If the source is unavailable, the screenshot fallback must carry the same tracking fields plus an explicit `GIF unavailable: source missing` notice; never silently substitute a still image.

## Decode policy

- Create run manifests and extracted frames in a unique temporary directory. Reuse fingerprint-keyed proxies and verification windows only when their adjacent `complete.json` marker matches and FFprobe validation passes; a media file without that marker is an interrupted artifact.
- On macOS, invoke only the bounded `workout_video_decode.py` entrypoint for original-media decoding, obtaining execution permission if required. Its uniform route tests the actual zero-copy VideoToolbox decode/filter/encode path at the start, middle, and end of every source. Exit code zero plus a VideoToolbox failure marker is failure, not success. Do not silently continue with a long software uniform decode.
- The entrypoint serializes original-media decodes with a lock, reports actual elapsed speed, and terminates a route whose projected runtime exceeds its budget. Record every attempt and fallback in the analysis manifest.
- Keyframe proxies must use `-threads 1 -skip_frame nokey`, retain a per-frame original timestamp map, and remain `coarse_only`. Sparse keyframes may locate broad activity but cannot justify an exact boundary or count.
- Preserve the source. Never overwrite or recompress the original workout video.
- If rotation metadata exists, normalize display orientation before visual judgment.
- Delete run-local temporary files after the report is safely archived. Retain the bounded fingerprint cache, completion markers, `segment-map.json`, and enough source segments in the report to reproduce every mapping. Cache reuse must avoid both decoding and another model pass for unchanged sources.

## Confusion-pair checks

Use these discriminators whenever either member of a pair is plausible:

- **Push-up vs quadruped preparation:** prove the push-up cycle before choosing a variant. Both hands must stay planted, both elbows must flex and re-extend, and sternum plus pelvis must travel together through at least two top-bottom-top cycles. Treat knee contact alone as weak pose evidence. Classify as preparation/transition when hips stay stacked over the knees, either hand leaves the floor, the person touches a phone/equipment, or the elbows stay nearly straight; these negative cues override periodic whole-body motion.
- **Standard vs knee push-up:** only after the push-up-cycle gate passes, confirm whether toes or knees bear weight during the descent and ascent, not during setup/end. Standard push-up requires a persistent shoulder-hip-ankle plank. Knee push-up requires persistent knee contact, unloaded lower legs, and a stable shoulder-hip-knee line through the complete bilateral elbow cycles.
- **Bulgarian split squat vs unsupported single-leg squat:** Bulgarian split squat has the rear foot fixed on an elevated support throughout the cycle; an unsupported single-leg squat has no fixed rear contact and the free leg moves with the body. In a front view, inspect the bench/bed contact and lateral shadow/occlusion rather than inferring from the visible front leg alone.
- **Bulgarian split squat vs ordinary split squat:** confirm whether the rear foot is elevated rather than planted on the floor.
- **Pike push-up vs standard push-up:** confirm the persistent high-hip body angle and predominantly vertical head path through multiple cycles.
- **Single-leg bridge vs floor transition:** confirm repeated hip extension cycles with one stable planted foot, rather than one lift used to reposition.
- **Shoulder press execution mode:** classify bilateral synchronous versus alternating (other arm at shoulder or overhead), then count sides independently. Report execution mode and per-side counts without doubling the total. A hidden side/phase triggers one dense window; if still unresolved, retain medium/low confidence and known-versus-pending counts. Use ±1 only for a genuinely bounded one-cycle ambiguity. Next time prefer one front-oblique camera 30-45 degrees off center; a second view is only needed for persistent severe occlusion.

## Accuracy rules

- Define the counted cycle explicitly for each exercise. Keep the definition consistent across all sets.
- Distinguish `completed reps`, `partial/aborted reps`, and `uncertain cycles`; never force uncertainty into an exact total.
- Do not infer left/right limb from anatomy alone when mirroring, camera angle, or rotation makes the side ambiguous.
- Use confidence per set (`high`, `medium`, `low`) and state the concrete reason for anything below high.
- Award `high` exercise-label confidence only after the classification evidence gate passes. Dense sampling increases temporal confidence but does not repair a missing support-contact or equipment-anchor observation.
- For new event evidence use schema v3 and fill `classification_audit`. A working set must have a wide-context intent of `working_set`, stable configuration, consistent cycle path, no setup/adjustment inside the declared work interval, and at least two complete cycles. A novel or one-off exercise also needs an agreeing wide-context second pass.
- Do not convert an environmental observation into a technique issue. State “no confirmed problem” when the adverse movement criterion is absent, even if a catalog contains a related issue ID or earlier sessions used that label.
- Before final totals, verify that each exercise summary exactly matches its timeline labels and chronological set numbers. Review every one-off exercise label and every unexpected variant against the nearest confirmed set.
- Derive exact seek points from source presentation timestamps for variable-frame-rate media. Otherwise state the sampling interval or uncertainty and avoid unsupported millisecond precision.
- Give form feedback in this order: immediate risk, whether the visible mechanics plausibly load the intended region, 1-3 highest-impact cues, and next filming requirement.
- Treat sharp pain, numbness, joint instability, or persistent pain as a stop signal and recommend in-person assessment; do not diagnose.

## Model consistency

- Run deterministic scripts for discovery, metadata, arithmetic, validation, GIF generation, indexes, and longitudinal aggregation.
- Ask the model only for exercise classification, disputed repetitions, visible technique judgment, and concise user-facing coaching language.
- Use stable catalog IDs and catalog-supplied correction cues. Do not let model wording create new exercise or issue identities.
- Reuse fingerprinted decode caches, but keep the counting judgment source-local and independent. Within the current source, a visual prototype may help navigation, exercise classification and form comparison only. Never use any prototype's repetition count, cadence or event spacing to count another set. Unchanged source frames that were already individually verified need not trigger another model call.
- Record the pipeline version and model identity when available, but keep historical facts independent of model choice.

## HTML report rules

When a workout page already exists, all the following content belongs inside that existing document. Standalone report delivery applies only when the project has no workout-page workflow. Keep data/evidence files separate from the single user-facing page.

- Always show: session summary, per-exercise set/repetition totals, visual timeline, an explicit color-to-exercise legend generated from the same mapping as the timeline bars, detailed timeline table, confirmed issue cards, corrections, correct-form learning links, source files, confidence, and analysis cost.
- For each issue or technique-focus card, require the local GIF whenever the source exists; use the retained source screenshot only for an explicitly unavailable historical source. Show the record type, training date and session label beside the GIF, then include file-relative timestamp, affected set/side/phase, narrow observation, correction cue, a local illustrated-guide link only when the project still uses illustrated tutorials, a `▶ 卡片内播放` button and direct new-tab link when a verified YouTube ID exists, and a `更多视频` search link.
- Treat `file://.../dashboard.html` as the standard user entry. Always retain a direct `https://www.youtube.com/watch?v=VIDEO_ID` link, and make file-mode tutorial buttons open it directly without an embed error or setup instructions. An optional HTTP view may embed `youtube-nocookie.com`, but the user-facing workflow must not depend on a server.
- Use relative paths from the report to project screenshots and guides so the report remains portable with the project folder.
- Keep the dashboard history index compact: date, title, summary, duration, confidence, per-exercise totals, total sets/reps, issue count, and report filename only. Do not duplicate detailed timelines or screenshots into the index.
- After updating the index, run the project rebuild. In the one-page-per-workout layout, verify the original workout URL contains its plan, actuals, full timeline, GIFs and cost, and that the dashboard links to that URL. Do not deliver a second report URL. Keep training evidence; do not create illustrated tutorial pages when the project has retired them.

- Fail report generation when any surfaced issue or actionable technique focus with an available source lacks an existing GIF, screenshot, correction or tracking fields. ## Token discipline

- Spend zero model-image tokens on metadata, audio peaks, motion curves, file ordering, and arithmetic.
- Skip audio decoding and transient analysis by default.
- Do not uniformly sample an entire long video at high frequency. Use coarse local signals, sparse representatives, then event-triggered dense scans.
- Reuse previously extracted frames and timestamps. Do not send both a dense contact sheet and the same full clip unless they resolve different uncertainties.
- Confirm one representative set per repeated visual setup for exercise classification and form comparison only. Count every set from its own source-local cycles; never copy, predict or regularize later counts from the representative set. Densely reclassify only when support contacts, equipment, camera angle, or motion pattern differ.
- Keep the classification pass separate from the form pass: first name the exercise from whole-body/support evidence, then crop or densify only the joints needed for technique review.
- Keep chat output compact; persist detailed timelines and evidence in local artifacts when the user wants recurring tracking.
- Report actual model-visible frames, contact sheets, short clips, resolution, and scan stages. Do not invent an exact token count or multiplier when measured usage is unavailable.

### Hard visual circuit breaker

- Create an analysis manifest at the start with `SKILL_DIR/scripts/analysis_manifest.py MANIFEST.json`. Record generated sheets separately from sheets actually shown to the model, plus dense windows, decoder attempts, and failed extra methods.
- Register each discovered set, source-local verification, and final count in that manifest. `--assert-final-ready` is a hard gate before report generation.
- Use sparse adaptive discovery pages within the frame/pixel budget; do not target a fixed number of coarse sheets. Repeated movements in the current source may reuse the first confirmed set as a classification/form prototype only; every set still requires its own independent cycle count. Each disputed issue or count gets at most one dense window.
- Track actual displayed frame slots and page pixels using the evidence contract, with readable page-size caps. Reserve budget for first/last cycles and disputed phases before discovery. At the selected budget, stop further viewing and record known cycles plus concrete unresolved coverage; do not manufacture ±1 or a high-confidence exact count. At most one extra local tracking method may be tried after disagreement. Only a new user-requested/approved review starts a new budgeted run.
- Local script outputs that the model never views do not consume the visual allowance, but must still be counted as generated artifacts. Copy the manifest counts into the report's `analysis_manifest` and user-facing cost section.
